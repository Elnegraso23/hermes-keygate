## Que estaba roto

`scripts/keygate-setup --reset-key` no reseteaba la bandera one-shot `.keygate-keyfile-served` cuando la DB operativa ya existia. El script imprimia `operative DB exists` y salia con `exit 0` **antes** de llegar al bloque que borraba la bandera.

Consecuencia directa: el `.key` del keyfile quedaba **irrecuperable desde la pagina web**. El endpoint `GET /api/onboarding/keyfile` respondia `410 Gone` para siempre y el boton de descarga aparecia muerto. Quien hubiera perdido su copia del `.key` (o tivesse.key de una instalacion anterior) se quedaba sin salida.

## Por que pasaba

El orden de las operaciones era el problema:

1. Parseo de argumentos (`--force` / `--reset-key`)
2. `if [ -f "$DB" ]` → si la DB existe y no hay `--force` → `exit 0`  ← **corte aqui**
3. ... creacion de DB, perfil de KeePassXC, verificacion
4. Bloque final: reseteo de la bandera `.keygate-keyfile-served`  ← **nunca se alcanzaba**

El reseteo estaba al final por heredar la estructura del script, pero es una operacion independiente de la DB: solo toca un archivo local `0600` que controla si el servidor sirve el keyfile una vez mas.

## El fix

Se extrajo el reseteo a una funcion `reset_key_flag()` y se invoca **antes** de cualquier `exit`, justo despues de definir `DB`/`KF` y parsear los argumentos. El bloque duplicado del final se elimino.

```bash
reset_key_flag() {
  local flag
  flag="$(dirname "$DB")/.keygate-keyfile-served"
  if [ -f "$flag" ]; then
    rm -f "$flag"
    echo "-- one-shot .key flag REMOVED: la web permite descargar el .key una vez más (tu decisión)"
  else
    echo "-- one-shot .key flag no existía: nada que resetear"
  fi
}

if [ "$RESETKEY" = 1 ]; then
  reset_key_flag
fi
```

## Por que es seguro

- La bandera es un archivo local `0600` que solo decide si la web sirve el keyfile una vez mas. Resetearla **no expone el `.key` por si solo**.
- El endpoint `/api/onboarding/keyfile` sigue exigiendo el `Authorization: Bearer` (la contrasena web) y el bind del servidor sigue siendo Tailscale/LAN.
- El keyfile **no se regenera**: `reset_key_flag()` no toca `~/.keepass-agent.key`, asi que tu `.key` descargado sigue siendo el valido.
- La DB operativa **no se toca**: `--reset-key` sin `--force` sigue sin reemplazar el vault.
- Es una accion local explicita y consciente, ya documentada en el README (`keygate-setup --reset-key`).

## Verificacion

- `scripts/keygate-selftest.sh`: **22 PASS, 0 FAIL** con el fix aplicado.
- Sandbox manual (HOME y vault temporales): el flag se borra, el vault sigue intacto y abrible con su keyfile (`keepassxc-cli ls` → exit=0, alias `Google`), y el keyfile no se regenera.
- Ciclo completo del endpoint verificado en un servidor aislado: primera descarga del `.key` → `200` con sha256 identico al keyfile del host; segunda descarga → `410`.

## Impacto para el usuario

- Cualquiera que hubiera perdido su `.key` con la DB ya creada recupera el acceso con `bash scripts/keygate-setup --reset-key` y vuelve a descargarlo una vez mas desde la pagina.
- Aclaracion importante para la documentacion: el `.kdbx` que se descarga **solo abre con el `.key` de la ultima descarga**. El `.key` corresponde al keyfile del host, no al vault: si el keyfile se regenera (por ejemplo, una reinstalacion), el `.key` viejo deja de abrir el `.kdbx` nuevo aunque el vault este intacto.

## Nota de seguridad

Tras un `--reset-key`, quien tenga la contrasena de la web puede volver a bajar el `.key` — es una decision consciente del owner y por eso el reseteo es local y explicito, nunca automatico. El `.key` no viaja por chat ni por Telegram: vive en el host (keyfile `0600`) y en la copia del usuario.
